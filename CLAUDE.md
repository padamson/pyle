# pyle

A library of the Leptos components my project landing pages are built
from, entirely: section components (the version switcher, a hero, code
tabs, the roadmap, and the rest) and a page component that frames them, so
a fix lands once for every site. A site supplies content, a theme, an
arrangement, and settings on each component; a section a site needs and
pyle lacks is built here. Each component gets theoria stories and leptotes
tests. Sites take pyle through git, pinned to a commit, and it is not
published to crates.io.

The workspace has one crate per job:

- `crates/pyle-core`: what a version is, which one is newest, and
  the `versions.json` shape. No Leptos and no filesystem, so it builds
  for the browser and for the CLI alike. It holds only what both the
  components and the CLI use.
- `crates/pyle`: the components, each in `src/components/` as
  `<name>.rs` beside its rules (`<name>.css`), its theoria stories
  (`<name>.stories.rs`), and its leptotes tests (`<name>.tests.rs`).
  `gallery.stories.rs` holds what the stories share and gathers them,
  for pyle's gallery and for a site's. `versions.rs` decides what the
  version bar shows, without Leptos, and `theme.rs` holds `Theme` and the
  one stylesheet, all of it in `@layer pyle`.
- `crates/pyle-cli`: the `pyle` binary, which copies a build into a
  static site one folder per version and writes `versions.json` and the
  root redirect. Checking out and pushing the site stay in each site's
  workflow.
- `crates/site`: pyle's own landing page, built with Trunk from pyle's
  components and nothing else. `SITE_VERSION` at build time names the
  snapshot it is (`dev` when unset), checked when it builds. Its `csr`
  feature is on in Trunk's build and off in a plain workspace build, so
  `cargo nextest run` tests pyle with no Leptos runtime turned on.
- `tools/gallery`: the theoria CLI, built in the workspace so it comes
  from the theoria commit `Cargo.lock` holds for the stories. `cargo
  theoria` (an alias in `.cargo/config.toml`) runs it.

`crates/pyle-e2e` sits outside the workspace with its own `Cargo.lock`:
the browser tests, which drive Chromium with playwright-rs. `site.rs`
deploys the site's snapshots with pyle-cli and tests them, `layers.rs`
tests the cascade between a site's stylesheet and pyle's on static pages
(two of them built by Tailwind and committed under `tests/fixtures/`), and
`gallery.rs` checks that every story renders with pyle's styles.

## Development

```bash
cargo build              # build
cargo nextest run        # run tests
cargo test --doc --workspace --all-features  # doc tests, with the ones behind `stories`
cargo clippy             # lint
cargo fmt                # format
cargo deny --workspace check bans licenses sources  # licenses, bans, sources
prek run cargo-lockpatrol --all-files  # advisories in every tracked Cargo.lock (ignore list: deny.toml)
cargo vet                # supply chain review
cargo theoria serve      # the component gallery, http://localhost:8081
(cd crates/site && trunk serve)  # pyle's landing page, http://localhost:8080
```

The browser tests need the built gallery, the built site, and Chromium:

```bash
cargo run --manifest-path crates/pyle-e2e/Cargo.toml --example install-browsers  # once
cargo theoria build
./scripts/site.sh        # target/site/dev, v0.1.0, and v0.2.0
cargo nextest run --manifest-path crates/pyle-e2e/Cargo.toml --config-file .config/nextest.toml --run-ignored all
```

## Claude Code sandbox

The sandbox is on in user settings for every repo, and a session never
writes outside its own working tree. `.claude/settings.json` (tracked)
adds this repo's part: two Mach lookups, for network configuration and
certificate trust, and the `excludedCommands` that run outside the
sandbox (`git`, `gh`, `cargo nextest run`, `cargo run`,
`./scripts/mutants.sh`, and `prek`). An exclusion applies only when the
Bash call is that one command: with a pipe or an `&&`, the whole call
runs sandboxed. So a session runs the browser tests itself, as the bare
`cargo nextest run` under Development; piped into `tail`, Chromium is
denied the Mach port it registers at launch and every test fails.

## Pre-commit hooks

```bash
cargo install prek
prek install --overwrite   # --overwrite replaces any legacy pre-commit hook
```

Hooks mirror CI checks: fmt, clippy, check, nextest, doctest, deny, vet,
and the skill version guard.

Before a session's first commit in a clone, it checks that
`.git/hooks/pre-commit` exists and that its second line reads
`# File generated by prek`. If either fails, the session stops and asks
the user to run `prek install --overwrite` from a plain terminal: the
install writes `.git/hooks`, which the sandbox protects. A commit made
without the hook goes in unchecked and nothing reports it, so a session
never says hooks ran on a commit it has not checked this way.

Run `prek` alone in its Bash call (Claude Code sandbox, above):
`git add -A && prek run --all-files` runs prek sandboxed, and
`end-of-file-fixer` fails opening `.claude/settings.json`.

## Manual checks

What a session cannot check and the person reviewing the work can. A
hand-off before a commit names each one that applies, as its command and
what a pass looks like; CI is the backstop, not the plan.

**From a plain terminal** (the sandbox blocks these):

- The pre-commit hook, once per clone: `prek install --overwrite`. A pass
  is `.git/hooks/pre-commit` with `# File generated by prek` as its second
  line.
- A change to `.claude/settings.json`: the sandbox denies writes to it,
  so apply the edit by hand, then run `/sandbox` in a new session. A pass
  is the resolved config showing the change.
- A new consumed skill: `npx skills add <owner>/<repo>` (Agent skills,
  below). A pass is one entry per skill in `ls -l .claude/skills/`.
- A new public API's rustdoc: `cargo doc --open`, since `open` is blocked
  in the sandbox.
- The GitHub settings, until the release ceremony deletes the script:
  `./scripts/github-settings.sh` (`--apply` to set what is off), after
  setup and after any change to the required checks or release tags
  (SETUP.md, "GitHub settings", lists what it sets). A pass is exit 0
  with only `ok` and `manual` lines. A session never runs it: these are admin
  changes, and its `gh` calls fail in the sandbox on purpose.
- The gallery, for a new or restyled component: `cargo theoria serve`, then
  each of its stories at http://localhost:8081. A session can start the
  server but cannot look at the page.
- pyle's landing page, for a change to it or to a component on it:
  `(cd crates/site && trunk serve)`, then http://localhost:8080. A pass
  is the page as you meant it, in light and in dark.
- The Tailwind fixtures, when the sites move to a new Tailwind release:
  change the version in `scripts/tailwind-fixtures.sh` and run it. It
  runs the Tailwind CLI Trunk downloaded for a site (or `TAILWINDCSS`),
  which a session may not reach. A pass is both `tailwind-*.css` under
  `crates/pyle-e2e/tests/fixtures/` opening with the new version's banner.

**Not from a session at all**, changed on github.com: creating the merge
App, installing it on the repo and generating its key, and Dependabot
malware alerts.

**By eye:**

- Prose a reader will act on: the CHANGELOG entry, README, the setup
  checklist while there is one, and the shipped skill under `skills/`.
  The skill version guard checks the bump, not that the prose is still
  true.
- A workflow change: the first run of the changed job on GitHub, since
  nothing local runs it. A job that only fires on a tag, a schedule or a
  Dependabot PR waits for that event, or a `workflow_dispatch` where it
  has one.

## Agent skills

`skills/pyle/` is the skill this crate will ship to consumers. It stays
hidden from installers (`metadata.internal: true`) until the first
component's API settles. Edits to it must bump `metadata.version` in its
`SKILL.md`; the pre-commit hook and the `Skill version guard` CI job both
enforce that.

Skills of tools this crate depends on are managed installs, not vendored:
`skills-lock.json` (tracked) records each source and a content hash, and
`npx skills add <owner>/<repo>` fetches the content into `.agents/` and
links it from `.claude/skills/`. Both paths are gitignored, so run the
installs once after cloning, from a plain terminal (the sandbox denies
writes under `.claude/skills/`). Verify with `ls -l .claude/skills/`: one
entry per installed skill. Refresh with `npx skills update -p`: without
`-p` it prompts for a scope and defaults to Global. The refresh runs fine
inside the sandbox, since the real files live under `.agents/`; only
`add`, which creates the `.claude/skills/` symlink, needs a plain
terminal. Confirm by reading `metadata.version` out of the installed
`SKILL.md`.

## Mutation testing

```bash
./scripts/mutants.sh                 # diff HEAD~1..HEAD (default)
./scripts/mutants.sh main            # diff main..HEAD
./scripts/mutants.sh --working       # diff uncommitted edits against HEAD
./scripts/mutants.sh -- --jobs 4     # pass extra cargo-mutants args
```

`scripts/mutants.sh` wraps `cargo mutants --in-diff`, scoping mutation
testing to just the lines a commit touched. A full-codebase run grows
linearly with codebase size and routinely takes hours; `--in-diff`
keeps the loop fast enough to use while the test is still warm. Use
`--working` to gate edits before committing them (new files need
`git add -N <file>` first to show up in the diff). Don't reach for
`cargo mutants -f <file>` as the fast path: with `examine_globs` set it
ignores the filter and sweeps everything in scope.

Run one mutation job at a time; every run writes `mutants.out/`. A
stray run is stopped with `pkill -f cargo-mutants` (hyphen; the binary
is `cargo-mutants`).

CI runs the per-diff variant on every push and PR, and the full-codebase
sweep only on `workflow_dispatch` — use it for occasional audits or big
refactors, never on a schedule. Both come from `security.yml`'s
`mutation` job, which calls `mutation.yml` in `padamson/rust-ci-workflows`.
The CI diff job computes its own diff and runs `cargo mutants --in-diff`
directly, not this script.

Scope the baseline with `.cargo/mutants.toml`, which ships live (a
`.mutants.toml` at the repo root is ignored silently); `--in-diff`
narrows from there.

## Tests

A test is a claim about behavior, named as the claim, one claim per
test, asserting the value (`assert_eq!` on an enum, `matches!` on the
error variant and what it names) rather than prose. The crates show the
shapes: a decision returned as a value (`pyle::notice`), an error that
carries the offending input (`pyle_cli::Error`), a `TempDir` fixture
(`crates/pyle-cli/tests/cli.rs`), and `#[ignore = "reason; run with ..."]`
as the gate for anything a fresh clone may lack (every test in
`crates/pyle-e2e`). Never `return` from a test because a precondition is
missing.

A component's claims go to the cheapest test that can hold them. What
the component decides is a plain function with unit tests
(`versions.rs`). What its first render holds is a leptotes test
(`<name>.tests.rs`). What the browser decides (the cascade, a fetch, a
navigation, anything after the first render) is a test in
`crates/pyle-e2e`: against pyle's own site when a real deploy shows it,
against a static page for the cascade, and against a story only for what
the gallery itself does. Every design decision about the components gets
its test here, not in a site. A site's theme is the
site's decision, so no story here copies one: the gallery shows the
default theme and the theme playground, and a site shows the components
under its own theme with `pyle::stories_for`.

`.config/nextest.toml` bounds every test with a slow-timeout; the hook
runs the default profile (no retries) and CI runs `--profile ci` (one
retry, reported FLAKY). nextest does not run doctests, so `cargo test
--doc` is its own step, and the workspace keeps at least one doctest so
that step is not a no-op (`pyle-core` has one at the top of its
`lib.rs`).

## Releases

pyle is `publish = false` and has no releases: sites depend on it through
git, pinned to a commit SHA, and that SHA is the version. `release.yml`
stays from the template so `scripts/github-settings.sh` can build the
release-tag ruleset and the `release` environment from it, but a tag
fails its first job, since no publishable crate matches. Publishing any
part of pyle (the version switcher is the likely one) is a separate
decision, and it starts by removing `publish = false`.
